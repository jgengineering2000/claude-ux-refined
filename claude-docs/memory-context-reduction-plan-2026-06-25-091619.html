Provenance note: this doc was committed (9753fe3) on a branch (docs/context-reduction-plan) that split off before the later master/PROCESS compression pass (12c8abc, a separate effort — see Sequencing below) and was never merged to main. Reconciled against actual MTI repo state and landed here 2026-07-13; the branch is unmerged and superseded by this version.

Problem

Sessions hit ~150k tokens within a minute of starting. The fixed always-loaded baseline (the claude_master.md + PROCESS.md + project CLAUDE.md chain ≈ 9k, plus MEMORY.md ≈ 3k) is not the driver. The driver is the file-based memory recall corpus: in MTI it had grown to 142 files / ~57k words, with broad multi-topic description: frontmatter that matches nearly any query, so a large fraction is injected into <system-reminder> blocks up front every turn.

This is a general (AUR-level) concern: any inheriting project accumulates memory the same way, so the remediation pattern belongs here, not only in MTI.

Phase 1 — Shipped in MTI (2026-07-13)

Done, commit 7bf1c19. All 76 project_*/feedback_* descriptions rewritten to a single "recall when X" trigger, ≤~15 words (worst case now 16 words — project_aur_role.md — down from a worst case of 72). Frontmatter-only; bodies untouched; verified via git diff --stat (76 files changed, 76/76 lines). The "verify the recall contract first" gate below was partially satisfiable: MEMORY.md's own header already documents that recall keys on each file's description: frontmatter, not body — confirmed from the source rather than re-derived. Whether ranking is top-K or match-all was not independently verifiable (harness internals, not something in either repo); narrowing to one trigger improves precision either way, so the phase proceeded without blocking on that unknown.

Why (original). The remaining files carry 40–72-word, multi-topic descriptions (e.g. one line spanning "test integrity + P1 correctness + 3 decisions + PY-3 + resume point"). Semantic recall matches these against almost any task, so over-firing persists. A tight, single-trigger description recalls a file only when it is genuinely relevant.

Approach

  • Verify the recall contract first. Confirm whether recall is top-K ranked or match-all, and that it keys on description: only (not body). The rewrite strategy differs: top-K → precision wins; match-all → narrowness directly cuts volume.
  • One file = one trigger. Rewrite each description: to ≤ ~15 words naming the specific condition under which the fact should surface, not a summary of its contents. The body already holds the detail.
  • Split, don't cram. Where a file legitimately covers two unrelated triggers, that is a signal it should be two memories (one fact per file — the standing rule).
  • Mechanical + reviewed. Draft new descriptions in a batch, diff old→new in a single review table, apply after sign-off. Frontmatter-only edits; bodies untouched.

Risk & mitigation

  • Risk: over-narrowing → a relevant memory stops surfacing. Mitigation: keep MEMORY.md (the always-loaded human index) as the safety net; it still lists every memory by hook, so a missed recall is recoverable by the index rather than lost.
  • Risk: payoff depends on recall internals. Mitigation: the verify-first step gates the whole phase.

Est. effort: ~90 frontmatter edits, one review gate. Est. payoff: fewer bodies per turn (exact depends on recall contract).

Phase 2 — Shipped in MTI, organically (verified 2026-07-13)

Shipped, but not the way this section originally proposed. There was no dedicated batch pass classifying every project_* file as ACTIVE/SETTLED. Instead, MEMORY-archive.md now exists and is in active use: MEMORY.md explicitly routes "low-per-turn-value pointers (inherited-AUR-rule anchors, SHIPPED work, the checkpoint trail)" there, and new memories get filed against that split as they're written (e.g. the 2026-07-13 Gemini-handoff memory). Net effect matches the goal — SETTLED content is out of the always-injected recall path but still retrievable by hand — achieved as an ongoing habit rather than a one-time reviewed batch. The .claude/memory-archive/ file-relocation option below was not used; the pointer-demotion option was, exclusively.

Why (original). Many project_* files describe work that is shipped, closed, or superseded (e.g. Q1 done, multiple phases shipped, CLOSED-invalid items). They hold "why we did X" value but should not front-load during active work — the same logic that moved the checkpoints, applied with per-file judgment because the knowledge is durable.

Approach

  • Classify each project_* file as ACTIVE (open work / live direction) vs SETTLED (shipped/closed/superseded). Git history + the file's own status markers drive the call.
  • SETTLED → .claude/memory-archive/ (out of the recall root, like checkpoints) or demote its pointer into MEMORY-archive.md while keeping the file recallable — choose per file:
    • Pure historical record (back-out lessons already internalised) → move out of recall.
    • Settled-but-still-referenced decision (an invariant other work cites) → keep recallable, tighten description (Phase 1).
  • Preserve linkage. Update [[wikilinks]] and the MEMORY.md / MEMORY-archive.md indexes so nothing is orphaned.
  • Never delete. Archive = relocate out of recall, always retrievable by hand.

Risk & mitigation

  • Risk: archiving a file that an active task actually needs. Mitigation: per-file judgment + the "still-referenced ⇒ keep recallable" carve-out; index pointer retained in MEMORY-archive.md.
  • Risk: losing the "why". Mitigation: nothing is deleted; durable rationale that belongs in a spec gets reconciled into the spec (existing spec-reconciliation work item).
